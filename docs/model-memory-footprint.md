# 모델별 RAM/VRAM 사용량 조사

jaeho/gunho/mooyaho(analysis_models의 약모델) 추가 서빙 작업 중 시스템 RAM OOM이 발생해서
원인을 조사한 기록. RTX 5070 Ti(16GB) + 시스템 RAM 30GB, 8개 모델
(yoojunho/junho/yongho/jaeho/gunho/mooyaho/best/best_judge) 상시 서빙 기준.

---

## 1. 사건 경위

`config.py`에 jaeho/gunho/mooyaho를 `SERVING_MODELS`에 추가하고 서버를 재시작하는
과정에서, 운영 서버(`uvicorn --reload`)의 파일 감시 자동 재시작과 별도로 띄운 테스트
프로세스가 동시에 겹쳐 8개 모델 프로세스 세트가 두 번 동시에 뜨는 상황이 발생했다.
KataGo 프로세스는 시작 시 TensorRT 엔진 튜닝 단계에서 프로세스당 순간적으로 큰 메모리를
쓰는데, 이게 겹치면서 커널 OOM killer가 KataGo 프로세스 7개와 무관한 데스크톱 세션
프로세스(wireplumber, pipewire, dbus-daemon 등)까지 강제 종료시켰다.

**교훈**: 위험한 건 정상 부하가 아니라 **여러 프로세스 세트가 동시에 뜨는 순간**이다.
운영 환경에서 `--reload`를 켜두면 파일 수정만으로 예고 없이 전체 프로세스가 재시작되므로,
수동 재시작과 겹칠 위험이 있다.

## 2. 모델별 RAM/VRAM 실측 (정상 가동, 유휴 상태)

`ps`(RSS) + `nvidia-smi --query-compute-apps`로 실측.

| 모델 | 넷 | RAM (RSS) | VRAM |
|---|---|---|---|
| yoojunho | b6c96 | 2.79 GB | 330 MiB |
| junho | b6c96 | 2.80 GB | 330 MiB |
| yongho | b6c96 | 2.79 GB | 330 MiB |
| jaeho | b6c96 | 2.81 GB | 330 MiB |
| gunho | b6c96 | 2.80 GB | 330 MiB |
| mooyaho | b6c96 | 2.79 GB | 330 MiB |
| best | b18c384nbt | 3.02 GB | 608 MiB |
| best_judge | b18c384nbt | 3.00 GB | 608 MiB |
| **합계 (8개)** | | **22.80 GB** | **3,196 MiB** |

**핵심 관찰**: b6c96(6블록, 5MB 파일)과 b18c384nbt(18블록, 98MB 파일)는 넷 크기가
20배 차이 나는데 **RAM은 8%밖에 차이 나지 않는다**. VRAM은 모델 크기에 정직하게
비례(330 vs 608 MiB)하지만, **RAM은 모델 크기와 거의 무관한 프로세스당 고정비용**이
지배적이다.

## 3. RAM 고정비용의 원인 — config 튜닝으로는 해결 안 됨

"프로세스당 고정 RAM이 KataGo의 스레드/캐시 설정 때문 아닐까" 가설을 세우고, 대표
약모델(junho, b6c96) 하나로 설정을 낮춰가며 실측했다.

| 설정 | numAnalysisThreads | nnCacheSizePowerOfTwo | nnMaxBatchSize | RSS |
|---|---|---|---|---|
| 원본(rtx_desktop.cfg) | 32 | 2²²(≈419만 엔트리) | 256 | 3.33 GB |
| 경량 시도 1 | 4 | 2¹⁶(64배 축소) | 32 | 3.59 GB |
| 경량 시도 2 | 4 | 2¹⁶ | **8** | 3.88 GB |

**세 knob(스레드 수/캐시 크기/배치 크기)를 전부 낮췄는데도 RAM이 줄지 않았다** —
오히려 측정마다 조금씩 늘었다(측정 시점 시스템 메모리 압박에 따른 노이즈일 가능성도
있음). `/proc/PID/smaps_rollup`으로 확인해보면 RSS의 93%가 `[heap]` 프라이빗 익명
메모리(공유 라이브러리 매핑이 아님)였다.

**결론**: 이 힙은 KataGo의 config 파일이 노출하는 파라미터로는 줄일 수 없고, TensorRT
엔진 런타임 자체의 내부 고정비용(실행 컨텍스트/활성화 버퍼/튜닝 테이블 등)으로 보인다.
정확한 내부 동작은 TensorRT 소스 레벨 확인이 필요해 단정할 수 없지만, "config 튜닝으로
해결 안 된다"는 실측 결론은 확실하다.

## 4. 용량 계획에 대한 수정 사항

기존 `review-ai-capacity-test-results.md`는 GPU **VRAM**만 측정했고, 이번에 처음으로
시스템 **RAM**을 실측했다. 결과가 다르다:

- VRAM: 8개 모델 합쳐 3.2GB / 16GB — 여유 큼, 병목 아님.
- **RAM: 8개 모델 합쳐 22.8GB / 30GB — 실질적 병목**. 모델을 하나 더 추가하려면
  최소 ~4GB의 여유가 더 필요한데, 지금 이미 그 정도밖에 안 남아있다.

→ **"모델을 몇 개까지 띄울 수 있는가"의 실제 상한은 GPU VRAM이 아니라 시스템 RAM이다.**
이전에 VRAM 기준으로 추정했던 "4~5개 더 가능"은 폐기하고, RAM 기준으로 재검토해야 한다.

## 5. OOM 방어 권장사항

1. **정상 가동 중 최소 4~5GB의 진짜 여유(available) RAM 유지.** 신규 모델 프로세스
   하나를 안전하게 추가하려면 그 시점에 최소 ~4GB 여유가 필요하다(정상 가동 3GB대 +
   TensorRT 튜닝 단계 순간 스파이크 여유분).
2. **(가장 중요, 구조적 조치) 동시에 두 프로세스 세트가 뜨는 상황 자체를 막는다.**
   이번 OOM의 진짜 원인은 부하가 아니라 재시작 충돌이었다. 운영 환경에서
   `uvicorn --reload`를 끄거나, 재시작 락(동시에 하나의 기동 시퀀스만 허용)을 걸어야
   한다.
3. 스왑(8GB)은 이번 조사 중 완전히 소진된 채로 관측됐고, KataGo 프로세스가 스왑아웃되면
   지연시간이 크게 튀므로 실질적인 안전판이 아니다. 스왑 증설보다 2번 조치가 우선이다.
