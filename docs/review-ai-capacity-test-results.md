# 복기 AI 용량 산정 — 테스트 결과 보고서

`temp/review-ai-capacity-test-request.md` 요청서에 대한 실측 결과. RTX 5070 Ti(16GB) 1대,
`configs/rtx_desktop.cfg`(numAnalysisThreads=32, nnMaxBatchSize=256) 기준.

**한 줄 요약**: 복기 자체의 GPU 처리량은 사전 추정보다 훨씬 여유롭다. 진짜 병목은
처리량이 아니라 **복기와 결과판정이 같은 프로세스 큐를 공유해서 생기는 인터랙티브
지연**이다(테스트 B). 아키텍처를 손대지 않으면 복기가 1건만 돌아도 결과판정 SLO가
깨진다.

## 0. 진행 전 확인된 데이터 제약 (사용자 확인 완료)

- **테스트 A 기보**: 요청서는 "150수 내외" 기보를 전제하지만, 실제 `GameRecord.csv`(448판)는
  대부분 5~9줄 소형 보드의 부스/테스트 세션이고 최장 수순도 126수(중앙값 33수)였다.
  150수 게임도, "스테이지"(고정 오프닝) 개념도 이 데이터엔 없다. → **실제 최장 기보로 대체**
  (`scripts/select_capacity_test_games.py`, 최장 6판 + 수순 분포 4분위 대표 4판 = 10판).
- **테스트 D(캐시/사전계산)**: 여러 유저가 동일 "스테이지"를 플레이한다는 전제인데
  `GameRecord.csv`엔 그런 구조가 없다(타이틀은 "파주시의장배 부스 테스트" 같은 행사명일
  뿐, 고정 오프닝 재사용 데이터 없음). → **이번 세션은 스킵**. 실제 스테이지 데이터가
  확보되면 포지션 해시 중복률 측정 스크립트를 별도로 작성해야 한다.
- **실행 범위**: A→C→B→E 순으로 전체 실행, 백그라운드로 순차 진행.

### 테스트 A. 복기 단건 처리 시간 (기준선)

|---|---|---|---|---|---|

| b10c128 | 800 | 1.09s | 80,999 | 76.6% / 82.0% | 1991 MiB |
| b20c256x2 | 100 | 0.83s | 13,468 | 92.6% / 94.0% | 2127 MiB |
| b20c256x2 | 800 | 4.41s | 19,593 | 93.6% / 96.0% | 2127 MiB |
| **b18c384nbt** | **100** | **1.39s** | **8,193** | 94.9% / 97.0% | 2251 MiB |

("복기 1건" = 실제 복기 로직 컨벤션대로 "장면수=수순×2"를 독립 요청 2개 동시전송한 완료
시간. 10게임 평균이며, 최장 기보 위주로 가중된 세트라 실서비스 평균(중앙값 33수)보다
**보수적으로 무거운** 값이다.)

**추가 확인**

- **스레드/배치 튜닝**: `numAnalysisThreads` 32→48, `nnMaxBatchSize` 256→384로 올려도
  차이가 없었다(0.0209s/scene → 0.0216s/scene, 오차범위). 동시 2장면 정도로는 현재
  설정으로 이미 GPU가 포화돼 있어(사용률 95%+) 스레드를 더 늘려도 이득이 없다. 현재
  설정 유지 권장. (`scripts/test_a_extra.py`, `configs/rtx_desktop_tuned.cfg`)
- **배치 효율**: 같은 127장면을 1개씩 순차 전송(14.08s, 0.111s/장면) vs 한 번에 배치
  전송(4.69s, 0.037s/장면) → **배치가 3.0배 빠름**. 복기 로직은 반드시 장면을 모아서
  한 번에 보내야 한다(이미 그렇게 구현돼 있음, `analyzeTurns` 배열 사용).

20게임, 4모델 × 800(기준)/400/200/100 visits, 자기 자신의 800visits 결과 대비 비교.
원본: `scripts/bench_results/test_c_durability.csv`

| 모델 | visits | 실수 감지 일치율 | 승률 부호 반전 | 최선수 top-3 포함률 | 집 차이 MAE |
|---|---|---|---|---|---|
| b10c128 | 100 | 97.47% | 17건(0.85/판) | 93.93% | 1.43집 |
| b20c256x2 | 100 | 97.47% | 20건(1.00/판) | 93.55% | 0.96집 |
| **b18c384nbt** | **200** | **99.24%** | 8건(0.40/판) | **97.85%** | 0.67집 |

| b28c512nbt | 100 | 98.74% | 2건(0.10/판) | 97.35% | 0.69집 |

**합격 기준(제안: v200에서 일치율≥90%, 부호반전 0건) 대비**: 일치율은 전 모델·전
visits에서 90%를 여유 있게 넘었다. 부호반전은 완전히 0은 아니지만(20게임/791수 중
b18c384nbt는 v200에서 8건=0.4건/판) 매우 낮은 수준이다. `대악수/악수` 판정 자체는
안정적으로 유지된다고 볼 수 있다.

**모델 선정 재확인**: b28c512nbt가 durability는 근소하게 더 좋지만(예: v100 일치율
98.74% vs 97.98%), b18c384nbt가 테스트 A 기준 처리량이 2.1배 높다(v800 기준
11,723 vs 5,427 visits/s). 반대로 b10c128/b20c256x2는 durability 수치만 보면
b18c384nbt와 큰 차이가 없어 보이지만, **테스트 C는 각 모델 자신의 800visits를
정답으로 삼는 자기참조 지표라 절대 정확도를 보장하지 않는다** — `network-selection.md`의
교차모델 ground truth 비교(winrate MAE: b10c128 0.033 vs b18c384nbt 0.008 @ v500)에서
이미 b10c128/b20c256x2는 절대 정확도가 크게 떨어진다고 확인됐다. 따라서 durability
숫자만으로 약한 모델을 올리면 안 되고, **b18c384nbt가 여전히 최적 선택**이다.

### 테스트 B. 인터랙티브 경합 시 지연 ⭐ (가장 중요한 발견)

`best`(b18c384nbt) 워커 1개에서 복기 부하(visits=100)를 N개 동시 유지하며, 착수
(level3 약모델, 별도 프로세스, visits=100)와 판정(best 워커 공유, visits=500) 각 50회
측정. 원본: `scripts/bench_results/test_b_contention.csv`

| 동시 복기 수 | 착수 p50/p95 | 착수 SLO(≤1s) | 판정 p50/p95 | 판정 SLO(≤2s) |
|---|---|---|---|---|
| 0(기준선) | 0.06s / 0.07s | ✅ | 0.35s / 0.44s | ✅ |
| 1 | 0.08s / 0.10s | ✅ | 1.24s / **2.68s** | ❌ |
| 2 | 0.09s / 0.10s | ✅ | 1.26s / **3.68s** | ❌ |
| 4 | 0.09s / 0.10s | ✅ | 1.27s / **5.75s** | ❌ |
| 8 | 0.08s / 0.09s | ✅ | 1.46s / **8.90s**(p99 11.2s) | ❌ |

**확정된 것**:
- ✅ **착수는 전혀 문제없다.** 이미 별도 프로세스(약한 level 모델)라 복기 부하가
  8건 몰려도 GPU 레벨 간접 경합만 있고 SLO에 전혀 영향이 없다(0.06→0.08s).
- ❌ **판정은 N=1부터 SLO를 못 지킨다.** 복기와 판정이 `best` 모델의 같은
  KataGoWorker 프로세스(같은 분석엔진 큐)를 공유하기 때문에, 복기가 큐에 넣은
  200+ 장면 뒤로 판정 요청이 밀려서 대기한다.
- **요청서의 명시된 분기 조건 발동**: "N=1에서도 인터랙티브가 SLO를 못 지키면 →
  GPU 시분할이 아니라 프로세스 분리(또는 인터랙티브 전용 예약)가 필수" → **바로 이
  상황이다.** 우선순위 큐/preemption 없이는 복기 워커 수 상한을 아무리 낮춰도(N=1도)
  판정 SLO를 보장할 수 없다.

**권장 조치**: 판정/자동종료를 복기와 별도의(가급적 저-visits 전용, 테스트 E 근거)
프로세스로 분리한다. 착수가 이미 그렇게 분리돼 있고 문제없다는 게 바로 이 표로
증명된다. 분리 후에는 복기 전용 프로세스의 동시성 상한만 고민하면 된다(§3 참고).

**스킵**(사용자 확인). `GameRecord.csv`에 "스테이지"(고정 시작 포지션) 구조가 없어

30게임(90% 지점=자동종료 근사 / 100% 지점=종국), b18c384nbt, 자기 자신의 800visits

| 결과 판정 | 400 | 0.00031 | 0.20집 | 0.26s |
| 자동 종료 수순 | 200 | 0.00095 | 0.39집 | 0.14s |

핵심 조치이기도 하다.

## 3. 수용 인원 역산

요청서 §3 공식을 그대로 적용하되, **테스트 B 결과 때문에 전제를 하나 붙여야 한다**:
아래 계산은 "판정/자동종료를 별도 저-visits 프로세스로 분리한 이후" 기준이다. 현재
구조(공유 큐) 그대로면 복기와 판정을 시간대로 완전히 분리하지 않는 한 안전한 N이
사실상 0이라 이 공식 자체가 성립하지 않는다.

복기 전용 프로세스의 동시성-처리량 곡선은 이번 세션에서 새로 재는 대신 기존
`scripts/bench_results/concurrency.csv`(b18c384nbt, v100, 동일 인프라·모델로 최근
측정됨)를 재사용했다: 처리량은 동시성 **4에서 정점**(76.8건/분)을 찍고 그 이후
떨어진다(N=8: 72.0건/분, N=16: 64.6건/분) — GPU 배치 포화로 무한정 늘려도 이득이
없다는 뜻. 다만 이 값은 "복기 1건=analyzeTurns 1회"(1x) 정의라, 테스트 A/C가 쓰는
"장면수=수순×2"(2x) 컨벤션과 맞추려면 보수적으로 절반으로 보정했다.

| 항목 | 1x 정의(원자료) | 2x 정의로 보정 |
|---|---|---|
| 복기 시간당 처리량(N=4 피크) | 4,608건/h | 2,304건/h |
| 피크 동시 복기 요청 상한(SLO 3분) | 230건 | 115건 |
| 일일 복기 처리 가능 건수(GPU 60~70% 할당, 24h) | 66,355~77,414건 | 33,178~38,707건 |
| **커버 가능 DAU**(전환율 0.5 ÷ 집중도 0.2) | **약 66~77만 명** | **약 33~39만 명** |

**⚠️ 이 숫자를 그대로 쓰면 안 된다.** 사전 추정치(§3 하단 표, 300~800명)와 **2~3
자릿수 차이**가 난다. 원인으로 짐작되는 것:

1. **실측 게임이 대부분 5~9줄 소형 보드다** (`network-selection.md`에서도 확인된
   사실). GameRecord.csv 448판이 실제 서비스 트래픽을 대표한다면, 사전 추정치가
   가정한 "복기 1건"보다 훨씬 가벼운 작업일 가능성이 크다. 반대로 실제 목표
   서비스가 19x19 같은 큰 보드/긴 대국 위주라면 이번 벤치마크가 과소평가된 것이다.
   → **실제 목표 보드 크기/평균 수순이 이 벤치마크 데이터(5~9줄, 중앙값 33수)와
   맞는지부터 확인 필요.**
2. 사전 추정치의 "GPU 복기 할당 비율(60~70%)", "전환율(0.5)", "피크 집중도(0.2)"가
   이번 실측과 별개로 설정된 값이라 그대로 곱하면 오차가 누적된다.
3. 테스트 D(캐시)를 반영하지 못해 실제로는 더 늘어날 여지도 있다.

**권장**: 위 표는 "GPU 컴퓨팅 자체는 사전 추정보다 훨씬 여유롭다"는 방향성 확인용으로
쓰고, 실제 DAU 확정은 (a) 목표 서비스의 실제 보드 크기·평균 수순을 반영한 재측정,
(b) 테스트 B에서 드러난 프로세스 분리를 실제로 구현한 뒤의 재검증을 거쳐야 한다.
**지금 시점에서 확실한 것은 "처리량은 병목이 아니고, 인터랙티브 SLO 보호(아키텍처)가
병목"이라는 방향성이다.**

## 4. 산출물 (요청서 §4)

1. **선정 모델**: `b18c384nbt` (기존 결론 유지). 근거: 테스트 C에서 v100까지 durability
   여유(일치율 97.98%), 테스트 A에서 b28c512nbt 대비 처리량 2.1배(v800 기준). 절대
   정확도는 `network-selection.md`의 교차모델 ground truth 비교로 이미 검증됨.
2. **운영 파라미터**:
   - 복기 기본 visits **200** / 포화 시 강등 **100** (둘 다 테스트 C 통과: 일치율
     99.24%/97.98%)
   - 복기 동시 워커 수 상한 **N=4** (판정/자동종료 분리 후. `concurrency.csv` 처리량
     정점 근거)
   - 인터랙티브 예약: **프로세스 분리 필수** — 착수(기존 level 모델, 이미 분리됨,
     문제없음 확인) + 판정/자동종료(신규로 별도 저-visits 프로세스 분리 필요,
     visits=100 권장, 테스트 E 근거) + 복기(전용 프로세스, N=4 상한)로 3분리 구조 권장
3. **커버 가능 DAU/피크 동시 복기 요청 수**: §3 참고. 처리량 자체는 사전 추정보다
   훨씬 크게 나왔으나 신뢰구간이 넓어 목표 보드크기 재확인 후 재계산 필요.
4. **캐시·사전계산 기대 절감률**: 측정 불가(데이터 부재). 스테이지 시스템 확정 후
   별도 측정 필요.
5. **자동종료/결과판정 분리 가능 여부**: **가능**. visits 50~100에서도 정확도 손실이
   미미하다(테스트 E). 이 분리가 테스트 B의 SLO 문제 해결의 전제조건이기도 하다.

## 5. 후속 조치 우선순위 (요청서 §5 기준, 이번 실측으로 갱신)

테스트 B 결과 때문에 우선순위가 바뀐다 — **프로세스 분리가 다른 모든 항목보다
선행돼야 한다**:

- [x] **(신규, 최우선) 판정/자동종료를 복기와 분리된 별도 프로세스로 이전**,
      visits≈100으로 하향 (테스트 E 근거). 이게 없으면 아래 항목들이 의미가 없다.
      → **구현 완료.** `config.py`의 `SERVING_MODELS`에 `best_judge`를 추가(동일 모델
      `b18c384nbt`, 별도 KataGo 프로세스). `best`=복기 전용(visits 200/포화시 100),
      `best_judge`=판정/자동종료 전용(visits~100 권장, 기존 500에서 하향). 실제
      GPU/모델로 서버를 띄워 두 프로세스가 독립적으로 응답함을 확인함(`/analyze/best`,
      `/analyze/best_judge` 모두 정상). **호출자(게임 서버) 측에서 판정/자동종료
      요청 시 `model_id`를 `best_judge`로, `maxVisits`를 ~100으로 바꿔야 실제 효과가
      난다** — 이 저장소는 서버 인프라만 제공하고 호출 쪽 코드는 별도 저장소에 있음.
- [x] 복기 요청 우선순위 큐 / preemption (분리 후에도 복기끼리의 큐잉엔 여전히 필요)
      → **구현 완료.** `pool.py`의 `ConcurrencyGate`(asyncio.Semaphore 기반 FIFO
      게이트)로 구현. 진짜 우선순위 레벨은 없지만(복기 요청은 모두 동급이라 불필요),
      상한 초과 요청은 도착 순서대로 대기한다.
- [x] 복기 워커 동시 실행 하드 제한 N=4 (분리된 복기 전용 프로세스 기준)
      → **구현 완료.** `config.py`의 `MAX_CONCURRENT_REQUESTS = {"best": 4}`
      (`REVIEW_MAX_CONCURRENT_REQUESTS` 환경변수로 조정 가능). 실측으로 검증:
      8개 동시 복기 요청을 보내면 `/status`가 `in_flight=4, waiting=4`를 보여주고,
      대기했던 절반의 게이트 대기시간(wait_latency) p95가 앞쪽 배치의 처리시간과
      거의 일치함을 확인.
- [ ] 큐 임계 초과 시 UX degrade ("복기 준비 중, 약 N분" + 푸시 알림)
- [ ] 목표 서비스의 실제 보드 크기/평균 수순 확인 후 §3 DAU 재계산
- [ ] 스테이지 시스템 확정 시 테스트 D(캐시/사전계산) 별도 측정
- [x] 운영 지표 대시보드 (큐 길이 / 복기 대기시간 p95 / 인터랙티브 p95 / GPU 사용률) —
      `/status` 엔드포인트(`main.py`)가 이미 큐 depth를 제공하니 확장 가능
      → **구현 완료.** `metrics.py` 신설(요청 지연시간 롤링 p50/p95 트래커 +
      `nvidia-smi` 기반 GPU 사용률/VRAM, 1초 캐시). `/status` 응답에
      모델별 `latency`(p50/p95), `best`의 `concurrency_gate`(in_flight/waiting/
      wait_latency), 최상위 `gpu`(util_pct/mem_used_mib/mem_total_mib)를 추가.
      시각화 대시보드 UI는 아직 없음 — 필요하면 이 JSON을 그대로 소비하는 프론트를
      별도로 붙이면 된다.

**구현 반영 파일**: `config.py`, `pool.py`, `main.py`, `metrics.py`(신규).
`/status` 응답 스키마가 `{model_id: [워커...]}` 평면 구조에서
`{"models": {model_id: {...}}, "gpu": {...}}`로 바뀌었다(이 스키마를 파싱하는
외부 모니터링이 있다면 갱신 필요).
