# KataGo 네트워크 선정 (복기 / 자동종료 / 결과판정)

## 배경

세 기능(복기, 대국 중 자동종료, 결과판정)에 공통으로 쓸 KataGo 네트워크와 maxVisits를 정한다.

제약조건:

- 세 기능 모두 **같은 모델**을 쓴다. 자동종료·결과판정은 대국당 1회만 호출되므로 정확도가 중요하고, 복기는 수순 수의 2배에 해당하는 장면을 한 번에 분석해야 한다.
- human-play용 네트워크는 제외.
- 복기는 사용자가 화면에서 결과를 기다리는 인터랙티브 UX이며, 서비스 성장에 따른 동시 사용자 증가를 감안해야 한다(나중에 모델을 낮추는 일이 없도록).
- 입문자/초보자 대상 앱이라 정확도가 완벽할 필요는 없다.

## 후보 선정

katagotraining.org의 네트워크 이력(946개) 전체를 크롤링해 elo/사이즈 기준으로 4세대를 골랐다 (human 계열 제외):

| 모델       | Elo     | 비고                          |
| ---------- | ------- | ----------------------------- |
| b10c128    | 11524.2 | 기존 `best`                   |
| b20c256x2  | 12906.7 |                               |
| b18c384nbt | 13623.4 |                               |
| b28c512nbt | 14107.7 | 다운로드되어 있던 최상위 모델 |

## 방법론

- **실제 운영 데이터** 사용: `GameRecord.csv`(448판). 보드 크기는 19x19이 아니라 대부분 5~9줄(13줄 1건)이었고 komi는 대부분 0.
- 보드 크기 분포를 보존한 층화추출로 50판 샘플링 (`scripts/prepare_positions.py`).
- **Ground truth**: b28c512nbt를 maxVisits=1000으로 돌려 각 턴의 winrate/scoreLead를 정답으로 저장 (`scripts/generate_ground_truth.py`). `canRecommendEnd` 필드는 검증에 사용하지 않음.
- **정확도 x 지연시간 sweep**: 4모델 x maxVisits(50/100/200/300/500)로 정확도(ground truth 대비 MAE)와 지연시간을 함께 측정 (`scripts/run_sweep.py`).
  - 주의: KataGo의 nnCache 때문에, 같은 포지션을 같은 maxVisits로 두 번 분석하면(예: 정확도 패스 직후 지연시간 패스) 두 번째 측정이 실제보다 5~10배 빠르게 나온다. 반드시 **maxVisits 조합마다 워커를 재시작해 콜드 캐시 상태**에서 지연시간을 재야 한다.
- **동시성 테스트**: 인터랙티브 복기 시나리오를 가정해 동시 리뷰 요청 1/4/8/16개를 시뮬레이션 (`scripts/test_concurrency.py`).

## 결과

### 정확도 x 지연시간 (콜드 캐시, `scripts/bench_results/sweep_v2_coldcache.csv`)

| 모델       | maxVisits | winrate MAE | score MAE | 단발 지연 |
| ---------- | --------- | ----------- | --------- | --------- |
| b10c128    | 500       | 0.0326      | 1.70점    | 0.07s     |
| b20c256x2  | 500       | 0.0338      | 1.14점    | 0.19s     |
| b18c384nbt | 100       | 0.0135      | 1.48점    | 0.08s     |
| b18c384nbt | 500       | 0.0077      | 1.22점    | 0.34s     |
| b28c512nbt | 100       | 0.0082      | 0.57점    | 0.15s     |
| b28c512nbt | 500       | 0.0025      | 0.23점    | 0.61s     |

nbt 계열(b18c384nbt, b28c512nbt)이 같은 visits에서도 구세대(b10c128, b20c256x2)보다 정확도가 3~4배 높다.

### 동시성 (`scripts/bench_results/concurrency.csv`)

인터랙티브 복기 요청(판 전체 analyzeTurns) 동시 N건일 때 요청당 지연시간(p50 / 최악):

| 모델       | maxVisits | 동시 1 | 동시 4       | 동시 8        | 동시 16       |
| ---------- | --------- | ------ | ------------ | ------------- | ------------- |
| b18c384nbt | 100       | 1.2s   | 2.5s / 3.1s  | 3.8s / 6.7s   | 9.8s / 14.9s  |
| b18c384nbt | 200       | 2.0s   | 4.4s / 5.4s  | 6.6s / 11.6s  | 17.4s / 26.4s |
| b28c512nbt | 100       | 2.6s   | 5.7s / 7.0s  | 8.7s / 15.0s  | 22.2s / 33.7s |
| b28c512nbt | 200       | 4.6s   | 9.9s / 12.1s | 15.1s / 26.3s | 39.8s / 59.9s |

GPU 처리량은 동시성 4 근처에서 정점을 찍고 그 이후로는 오히려 떨어진다 — 동시 요청을 늘려도 전체 처리량은 늘지 않고 개인별 대기시간만 늘어난다.

## 결론

**공통 모델: b18c384nbt**

| 용도                       | maxVisits | 근거                                                                                               |
| -------------------------- | --------- | -------------------------------------------------------------------------------------------------- |
| 복기 (대기형)              | ~100      | 동시 16명에도 p50 9.8s/최악 14.9s로 여유. b28c512nbt는 동시 8명만 몰려도 최악 15~26s로 UX에 부적합 |
| 자동종료 / 결과판정 (단발) | ~500      | 대국당 1회라 동시성 영향이 작고(단발 0.34s), 정확도를 더 확보할 여유가 있음                        |

b28c512nbt(elo 14107.7)가 정확도는 더 높지만(winrate MAE 0.0082 vs 0.0135 @ v100), 동시 사용자 환경에서 지연시간이 항상 2배 이상 나쁘다. 입문자 대상 앱에서 이 정도 정확도 차이는 체감되기 어려운 반면 지연시간 차이는 바로 체감되므로, 동시성 여유를 우선했다.

maxVisits는 서버 config가 아니라 요청 payload로 넘기는 값이라, 실제 반영은 클라이언트(호출부) 쪽에서 두 용도에 맞게 나눠 보내야 한다.

## 재사용 가능한 도구

| 스크립트                           | 역할                                                  |
| ---------------------------------- | ----------------------------------------------------- |
| `scripts/prepare_positions.py`     | GameRecord.csv에서 층화추출로 테스트용 포지션 셋 생성 |
| `scripts/generate_ground_truth.py` | 최강 모델 고-visit 분석으로 ground truth 생성         |
| `scripts/run_sweep.py`             | 모델 x maxVisits 정확도/지연시간 sweep (콜드 캐시)    |
| `scripts/test_concurrency.py`      | 동시 사용자 부하에서 요청당 지연시간 측정             |
| `scripts/bench_networks.py`        | 합성 착수 기반 빠른 스팟 체크 (정확도 비교엔 부적합)  |
| `scripts/kg_bench_lib.py`          | 위 스크립트들이 공유하는 워커 기동/payload 헬퍼       |
| `utils/sgf_parser.py`              | SGF ↔ KataGo 좌표 변환                                |

새 네트워크가 나오면 `scripts/bench_models.json`에 추가하고 `run_sweep.py` → `test_concurrency.py` 순으로 재실행하면 된다.

## 참고 / 한계

- 정확도 검증은 448판 중 50판 표본 기준. 표본을 늘리면 신뢰구간이 더 좁아진다.
- 이 저장소(katago-server)는 KataGo 서빙만 담당하며, 용도별 maxVisits 분기는 호출하는 애플리케이션 쪽 구현이 필요하다.
