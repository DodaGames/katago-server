# 복기 AI 용량 산정 — 테스트 요청서

출시 전 **AI 모델 선정**과 **단일 GPU 서버의 수용 인원 산정**을 위한 측정 요청서입니다.
KataGo Analysis Engine 기준으로 작성했습니다.

- **목적 ①**: 출시 후 감당 가능한 DAU / 피크 동시 복기 요청 수를 숫자로 확정
- **목적 ②**: 부하가 걸려도 **모델을 교체하지 않고** 버틸 수 있는 모델을 선정

---

## 0. 배경 — 왜 이 테스트가 필요한가

### 제약 조건

| 항목 | 현황 |
|---|---|
| 인프라 | GPU 데스크탑 **직접 구매 1대** → 수평/수직 확장 불가 |
| 강한 AI 사용처 | 복기, 자동 종료 수순 제공, 결과 판정 |
| 약한 AI 사용처 | AI 대국 |
| 복기 연산량 | **총 수순 × 2** 장면을 한 번에 분석 → 단일 요청이 매우 무거움 |
| 모델 교체 | 특정 모델 기준으로 복기 로직을 작성 → **교체 시 로직이 깨질 위험** |

### 핵심 리스크

> 복기에서 연산이 포화되면 **AI 대국·자동 종료·결과 판정까지 같이 죽는다.**

복기는 배치성 작업이라 몇 분 늦어도 UX로 방어할 수 있지만,
대국 중 착수 응답이 늦어지는 건 방어할 수 없습니다.
따라서 **두 워크로드를 같은 GPU에서 자유 경쟁시키면 안 되고**, 그 경계선을 숫자로 알아야 합니다.

### 설계 원칙 — 부하 조절 다이얼은 모델이 아니어야 한다

| 다이얼 | 복기 로직 영향 | 채택 |
|---|---|---|
| 모델 교체 | 판정 결과 자체가 바뀜 | ❌ 금지 |
| **visits 상한 조정** | 정확도만 저하, 판정 구조는 유지 | ✅ 주 다이얼 |
| 큐 대기 시간 | 없음 | ✅ 보조 다이얼 |
| 분석 장면 수 축소 | 중간 (복기 완성도 저하) | △ 최후 수단 |

→ 그래서 모델 선정 기준은 **"목표 visits에서 얼마나 정확한가"가 아니라
"visits를 바닥까지 낮췄을 때도 판정이 안 뒤집히는가"** 입니다. (테스트 C)

---

## 1. 목표 SLO (이 테스트가 검증할 기준)

측정 결과를 이 기준에 대입해 수용 인원을 역산합니다.

| 워크로드 | 성격 | 목표 |
|---|---|---|
| 착수 응답 (AI 대국) | 인터랙티브 | p95 **≤ 1s** (하드 보장) |
| 자동 종료 수순 / 결과 판정 | 인터랙티브 | p95 **≤ 2s** (하드 보장) |
| 복기 (제출→완료, 큐 대기 포함) | 배치 | p95 **≤ 3분** |

---

## 2. 측정 항목

### 테스트 A. 복기 단건 처리 시간 (기준선)

**목적**: 복기 1건의 순수 비용 확정

**방법**
- 후보 모델별로 실행 (예: `b18c384`, `b28c512` 등 검토 중인 전체)
- 입력 기보: **150수 내외 실제 스테이지 기보 10건** (짧은/긴 판 섞어서)
- 실제 복기 로직과 동일한 장면 수(수순 × 2)로 요청
- GPU에 **다른 부하 없는 단독 상태**에서 측정

**기록할 값**

| 모델 | visits/장면 | 총 장면 수 | 복기 1건 소요(s) | 배치 상태 visits/s | GPU 사용률 | VRAM |
|---|---|---|---|---|---|---|
| | 100 | | | | | |
| | 200 | | | | | |
| | 400 | | | | | |
| | 800 | | | | | |

> visits 4단계 × 모델 수만큼 측정해 주세요. **visits/s 실측치**가 이후 모든 계산의 기준이 됩니다.

**추가 확인**
- Analysis Engine의 `numAnalysisThreads` / `nnMaxBatchSize` 튜닝 전후 차이
- 한 번에 여러 장면을 보낼 때의 **배치 효율** (장면 1개씩 vs 300개 한 번에)

---

### 테스트 B. 인터랙티브 경합 시 지연 (가장 중요)

**목적**: 복기가 돌고 있을 때 대국/판정이 얼마나 느려지는지 = **포화 임계점 찾기**

**방법**
1. 복기 워커를 **동시 N개** 가동 (N = 1, 2, 4, 8)
2. 그 상태에서 AI 대국 착수 요청 / 결과 판정 요청을 각각 50회 이상 발생
3. 인터랙티브 요청의 **p50 / p95 / p99** 응답 시간 기록

**기록할 값**

| 동시 복기 수 | 착수 p95 | 판정 p95 | 복기 1건 소요 | 판정: SLO 충족? |
|---|---|---|---|---|
| 0 (기준선) | | | — | |
| 1 | | | | |
| 2 | | | | |
| 4 | | | | |
| 8 | | | | |

**이 테스트로 확정할 것**
- ✅ **복기 동시 실행 허용 개수 (워커 수 상한)** — 인터랙티브 p95가 SLO를 넘지 않는 최대 N
- ✅ 우선순위 큐 / preemption이 필요한지 여부

> 만약 N=1에서도 인터랙티브가 SLO를 못 지키면 → **GPU 시분할이 아니라 프로세스 분리(또는 인터랙티브 전용 예약)** 가 필수라는 뜻입니다. 이 경우 별도 보고 부탁드립니다.

---

### 테스트 C. 모델별 "바닥 visits" 내구성 ⭐

**목적**: **모델 교체 없이** 부하를 견디려면, 낮은 visits에서도 복기 판정이 유지되어야 함

**방법**
- 동일 기보 20건에 대해 각 모델을 `visits = 800 / 400 / 200 / 100` 으로 복기 실행
- **800 visits 결과를 정답(reference)** 으로 두고, 낮은 visits 결과와 비교

**비교 지표 (복기 로직이 실제로 쓰는 출력 기준)**

| 지표 | 판정 기준 |
|---|---|
| 실수(악수) 감지 위치 | 정답 대비 **일치율 %** |
| 승률 그래프 방향 | 부호가 뒤집힌 구간 수 |
| 추천 수(최선수) | 정답의 top-1 / top-3 포함률 |
| 집 차이 추정 | 평균 절대 오차 (집) |

**기록할 값**

| 모델 | visits | 실수 감지 일치율 | 승률 부호 반전 | 최선수 top-3 포함률 | 집 차이 MAE |
|---|---|---|---|---|---|
| | 400 | | | | |
| | 200 | | | | |
| | 100 | | | | |

**합격 기준 (제안)**
- `visits = 200`에서 실수 감지 일치율 **≥ 90%**, 승률 부호 반전 **0건**
- → 이 조건을 만족하는 모델 중 **visits/s가 가장 높은 것**을 선정

> 이 기준을 통과하면, 포화 시 visits만 낮춰서 처리량을 2~4배 확보할 수 있고
> **복기 로직은 손대지 않아도 됩니다.**

---

### 테스트 D. 캐시 / 사전 계산 효과 (부하 절감)

**목적**: 스테이지는 정해진 문제라 초반 수순이 동일 → 중복 연산 제거 여지가 큼

**방법**
- 동일 스테이지의 서로 다른 유저 기보 30건을 순차 복기
- 포지션 해시 기준 **중복 장면 비율** 측정
- KataGo 트리 재사용 / 결과 캐시 적용 전후 처리 시간 비교

**기록할 값**
- 스테이지별 장면 중복률 (%)
- 캐시 적용 시 복기 1건 소요 시간 감소율 (%)
- 사전 계산(precompute) 대상으로 삼을 만한 상위 분기 규모 (장면 수 / 저장 용량)

---

### 테스트 E. 자동 종료 / 결과 판정의 최소 요구 성능

**목적**: 이 둘이 정말 "강한 모델 + 높은 visits"를 필요로 하는지 확인
→ 불필요하다면 복기 경로에서 분리해 인터랙티브 예산 확보

**방법**
- 종국 기보 30건에 대해 사석 판정 / 집계산을 `visits = 400 / 200 / 100 / 50`로 실행
- 정답(사람 검수 또는 800 visits) 대비 판정 정확도 측정

**기록할 값**

| 용도 | visits | 판정 정확도 | 소요 시간 |
|---|---|---|---|
| 자동 종료 수순 | 400 / 200 / 100 / 50 | | |
| 결과 판정 | 400 / 200 / 100 / 50 | | |

> 낮은 visits에서도 정확도가 유지되면 **인터랙티브 전용 경량 경로**로 분리합니다.

## 3. 결과 활용 — 수용 인원 역산식

측정치를 아래 식에 대입해 최종 숫자를 확정합니다.

```
복기 1건 소요(s)          = 테스트 A
복기 동시 워커 수 N       = 테스트 B (SLO 만족 최대치)
복기 시간당 처리량        = 3600 / 복기1건소요 × N

피크 동시 복기 요청 상한  = 처리량 × (SLO 3분 / 60)
일일 복기 처리 가능 건수  = 처리량 × 피크시간 환산

커버 가능 DAU
  = 일일 복기 가능 건수 ÷ 복기 전환율(0.5) ÷ 피크 집중도(0.2)
```

**참고 — 사전 추정치 (실측으로 대체될 값)**

| 항목 | 추정 |
|---|---|
| 복기 1건 | 40~130s (모델에 따라) |
| GPU 복기 할당 비율 | 60~70% (나머지 인터랙티브 예약) |
| 복기 처리량 | 시간당 25~50건 |
| 피크 동시 복기 상한 | 5~10건 |
| **커버 가능 DAU** | **300~800명** |

→ 실측 결과가 이 범위와 크게 다르면 출시 전 아키텍처 재검토가 필요합니다.

## 4. 산출물

테스트 완료 후 아래를 회신 부탁드립니다.

1. **선정 모델 1종** + 근거 (테스트 C 합격 여부, 테스트 A visits/s)
2. **운영 파라미터 3종**
   - 복기 기본 visits / 포화 시 강등 visits
   - 복기 동시 워커 수 상한
   - 인터랙티브 예약 비율 (또는 프로세스 분리 여부)
3. **커버 가능 DAU / 피크 동시 복기 요청 수** (§3 역산 결과)
4. 캐시·사전 계산 도입 시 기대 절감률 (테스트 D)
5. 자동 종료 / 결과 판정 분리 가능 여부 (테스트 E)

---

## 5. 후속 (테스트 결과 확정 후 구현)

- [ ] 복기 요청 **우선순위 큐** — 인터랙티브가 항상 복기를 preempt
- [ ] 복기 워커 **동시 실행 하드 제한** (테스트 B 결과값)
- [ ] 큐 임계 초과 시 **UX degrade** — "복기 준비 중, 약 N분" + 푸시 알림 전환
- [ ] 스테이지 복기 **오프피크 사전 계산** 배치
- [ ] 자동 종료 / 결과 판정 **경량 경로 분리**
- [ ] 운영 지표 대시보드 — 큐 길이 / 복기 대기시간 p95 / 인터랙티브 p95 / GPU 사용률
